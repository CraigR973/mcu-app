# Brand integration — what the app ships and where it came from

The approved identity is the **three-case-and-disc family** in
`docs/brand/logo-system/stack-family/`, generated by
`docs/brand/logo-system/build_stack_identity.cjs`.

**Both directories are in git.** `docs/brand/` went in on 10 Sep (`fb6ecbd`), third-party
images included. **Since Batch U3 those images are untracked and ignored** (Craig's pick B,
`OWNER-ACTIONS.md` 15, `DECISIONS.md` #221): `source-images/`, every
`logo-system/concepts/*/sources/`, `concepts/catalogue-frame-v2/poster-source-grid.png`,
and any JPEG under `docs/brand/`. They stay on disk where they were, and in history before
U3; removing them from history is a rewrite only Craig can run. This file is the bridge: it
records which asset ships, which surface uses it, and how to regenerate the pair.

**What a clean clone can rebuild** (checked in U3, with sharp 0.35.4).
`build_stack_identity.cjs` reads only tracked files: `wordmark-dark.svg` and the two
masters in `concepts/poster-stack-v2/` (`poster-stack-concept-art-v1.png`,
`poster-stack-actual-posters-v1.png`). Run on a tree with the images untracked, it rebuilt
every icon, mark, lockup and the social card: the SVGs byte for byte, and 38 of its 42
PNGs pixel for pixel. The other four are the 180 and 192 px resamples, within 2 of 255
levels, a newer image library's rounding. The two photographic heroes cannot be rebuilt:
`build_photo_hero.py` reads `source-images/`, and `hero-photo-v3.png`'s builder was never
committed. Their finished files stay tracked.

```bash
# regenerate the design system (needs sharp; see stack-family/README.md)
node docs/brand/logo-system/build_stack_identity.cjs

# install the shipped subset, or report drift
node scripts/brand-sync.mjs
node scripts/brand-sync.mjs --check
```

`brand-integration.test.ts` makes the same comparison in CI, over every file in
`apps/web/public/brand/`, and fails if a third-party image is tracked again.

## The responsive hierarchy, as the app applies it

The system is responsive by *drawn artwork*, not by scaling one file. `BrandMark` picks
the tier; `apps/web/src/components/brand/brand.test.tsx` pins the table down.

| Rendered size | Artwork | Where the app draws it |
|---|---|---|
| >= 192 px | concept-art emblem | platform icons only — manifest, Apple touch, notification |
| 128–191 px | display vector mark | reserved display contexts |
| 32–127 px | compact optical mark | loading states (64), sidebar (40), mobile and onboarding headers (32–36), offline page (32) |
| < 32 px | pixel-hinted micro mark | the 16 px entry of `favicon.ico` |

Lockups are separate: horizontal (>= 280 px) for wide positions, stacked (>= 320 px) for
square ones. The desktop sign-in page uses the complete horizontal lockup at 440 px, where
it remains legible without introducing the stacked artwork's square field into a tall
editorial panel. `BrandLockup` warns in development when a call site goes under a minimum
without recording why.

## Two rules that constrain what may ship

**The personalised poster edition is private and ceremonial.**
`personalised-poster-icon-*` and the photographic `hero-photo-*` wordmarks are built from
real film stills and publicity photographs. They are commemorative artwork, not the
rights-independent identity. The poster therefore appears once, at 192 px in the
authenticated onboarding welcome; it is not navigation chrome, loading artwork, an app
icon or a share card. The share card is the rights-independent horizontal lockup on the
ink field.

**Semantic interface colours are not brand colours.** The identity is carried by the
artwork, which brings its own palette inside each SVG and PNG. No semantic token was
retuned to match it, and none needed to be — see `DECISIONS.md` #135.
