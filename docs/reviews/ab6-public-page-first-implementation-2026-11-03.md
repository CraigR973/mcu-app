## How collection works now, under review

Vue's active today/tomorrow dates are selected first. If none match the requested window,
Vue makes no request. Otherwise one ordinary public programme page GET runs before the
existing date GETs in the same HTTP client. Its known venue title must be present after
existing status/challenge/body checks; wrong or unrecognised pages fail before any date
request. The client handles ordinary host-scoped cookies in memory; no values/headers
enter snapshots, logs or storage. No copied cookie, login, browser, script download,
redirect, challenge solving, private token, new provider/service or credential.

The extra GET/bytes/time count inside the existing combined 120 GET/12 optional metadata/
five-minute/64 MiB limits, 15s and 2 MiB per response/two slots/one start per second per
host. Source refusals stop the host; any page/date failure fails the whole Vue snapshot.
A successful prefix remains diagnostic/excluded from metadata and promotion. Other source
adapters, strict identity/category definitions and the all-nine gate are unchanged.
The ab6-3 artifact version identifies this protocol; older reviewed artifacts are rejected,
not silently promoted or patched with the later Vue experiment. No data shape/migration,
public API/zod contract, schedule or hosting diff is added by this amendment.

Design decisions made under #334: validate the ordinary page's observed venue title;
reuse the existing client/budget; preserve whole-Vue failure; reject older protocol
artifacts. The page-first sequence succeeded once in #333, but cookie causality and
recurring availability remain unproved. A fresh all-nine sample is still needed.
